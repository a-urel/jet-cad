## What pub.dev does (verified 2026-10-13, not assumed)

Read from the source at pub-dev `1fefbf5`, pana `9911b2d`, pub `9df389a`
(each `main` on 2026-10-13), dart.dev and GitHub's documentation.

- **A relative image in a README** is never served from the archive. pana's
  repository verification rewrites it to
  `https://github.com/<owner>/<repo>/raw/<default branch>/<package dir>/<path>`
  (`lib/src/repository/repository_url_resolver.dart`); with no verified
  repository the image is dropped for its alt text
  (pub-dev `app/lib/shared/markdown.dart`). The ref is the default branch
  detected at analysis time, **never the tag**, so every past version shows
  what the default branch holds now (pub-dev #5859). dart.dev's "Writing
  package pages" advises absolute URLs. Every image goes through
  `external-images.pub.dev` (10 MB per image, 8 s timeout).
- **`screenshots:`** is a list of `description` + `path`. pana takes at
  most 10, each at most 4 MB (4×1024×1024), a description of at most 160
  characters (`lib/src/screenshots.dart`); pub.dev's upload rejects a
  description under 10 or over 200 characters, a path not equal to its
  normalised form, a duplicate, or a file missing from the archive
  (`pkg/pub_package_reader`). Formats: png, jpg, gif, webp (pana converts
  to webp and makes 100 px and 190 px thumbnails; the first screenshot is
  the package's thumbnail). **`dart pub publish --dry-run` does not
  validate the field**; a bad screenshot sets pana's "Package has an
  example" to 0/10.
- **`.pubignore`** is gitignore syntax per directory, and replaces that
  directory's `.gitignore`; dotfiles (`.github/`) never ship. A screenshot
  must be in the archive, so it must not sit under `test/`, `tool/` or
  `build/`, which the packages' `.pubignore` files exclude. Limits: 100 MiB
  compressed, 256 MiB uncompressed; pub only hints above 100 MB.
- **`funding:`** is a non-empty list of `https` URLs of at most 255
  characters each (an upload check). pana HEAD-checks them: an invalid one
  costs the pubspec's 10 points, an unreachable one only an issue. pub.dev
  shows them in a sidebar block "Funding", each link named by its host. No
  points for having them.
- **`.github/FUNDING.yml`** takes `github: <user>` and
  `buy_me_a_coffee: <user>`.

## Purpose

A visitor on pub.dev sees what each package draws before reading a line,
knows which of the three a host installs (only the planner), finds the
host guide and the other two packages in one click, and can support the
project. Everything shown is produced by a command in the repository and
every code snippet in a README is code CI analyses.

## D4. Generating the screenshots: `tool/screenshots`

A new workspace member, `tool/screenshots`: a Flutter package,
`publish_to: none`, depending on the three published packages and on
`jet_cad_restaurant_symbols` (none of which depend on it, so no cycle, and
the published packages gain no dependency). Like every member, it names
the published packages by hosted caret (`^0.7.2`), which the workspace
resolves to the local copies (`tool/ci/test/dependency_lines_test.dart`
covers it, as it will `tool/readme_probe`). It holds:

- `lib/scenes.dart`: one function per scene (D5), each building its widget
  tree from **public API only** — the barrels, plus `editor.dart`'s
  `startupPlan` for the renderer's drawing — at a fixed logical size of
  1280×800 and a fixed device pixel ratio (D6).
- `test/screenshots_test.dart`: pumps each scene, loads the real fonts,
  settles, and captures the scene's `RepaintBoundary` with `toImage` inside
  `runAsync`. With `UPDATE_SCREENSHOTS=1` in the environment it writes each
  PNG to `packages/<package>/doc/screenshots/<name>.png`; without it, it
  asserts that every scene builds and paints with no exception and with
  real fonts, and **compares no pixels**, so CI on Linux renders the same
  scenes without failing on rasteriser and font-hinting differences from
  macOS. The idiom is the restaurant demo's `UPDATE_SAMPLES=1`
  (`apps/restaurant_demo/test/sample_plans_test.dart`).
- The command, stated in the package's README and the results note:
  `cd tool/screenshots && UPDATE_SCREENSHOTS=1 flutter test`.

**Fonts.** The package declares `uses-material-design: true` and the
`Roboto` family from `packages/jet_cad_floor_plan/fonts/Roboto-Regular.ttf`
(as a host does). Before pumping, the test reads the test bundle's
`FontManifest.json` and loads every family through `FontLoader`, which
gives the planner's text and its chrome icons (MaterialIcons) real glyphs
instead of Ahem and empty boxes. The plan's first task proves this
(a probe glyph's advance differs from Ahem's 1 em, and an icon paints ink);
if MaterialIcons is not in the test bundle, the fallback is reading
`MaterialIcons-Regular.otf` from `$FLUTTER_ROOT/bin/cache/artifacts/material_fonts/`,
failing loudly when it is missing. Which route holds is recorded.

**Reproducible, not pixel-stable.** The same command on the same Flutter
(3.47.6, CI's pin) makes the same scenes; the PNGs are regenerated by
running it, never edited by hand. They are documentation, not a contract,
so no golden compares them.

## D6. Size and placement

- Logical 1280×800; the device pixel ratio is 1.5 unless a measured file
  exceeds the budget, in which case 1; the choice and the measured sizes are
  recorded in the results note.
- **Budget:** each PNG at most 1 MB, each package's screenshots together at
  most 4 MB. `dart pub publish --dry-run`'s archive size for both packages
  is recorded before and after.
- `screenshots:` in the renderer's pubspec lists R1–R5, the planner's
  P1–P6, each with a description of 10–160 characters; R1 and P1 come first
  (the thumbnail).
- **In the READMEs:** the renderer's shows R1 under its first paragraph and
  R2–R5 in a "Screenshots" section; the planner's shows P1 and P3 at the
  top and P2, P4–P6 in "Screenshots". Every image URL is absolute and
  pinned to the package's release tag:
  `https://raw.githubusercontent.com/a-urel/jet-cad/<package>-v0.7.2/packages/<package>/doc/screenshots/<file>`,
  so each published version keeps its own pictures. Cost: on GitHub the
  images are broken from the merge until the human pushes the tag.

## D7. `tool/ci/check_screenshots.dart`

Pure Dart, in `tool/ci` with tests beside the existing ones. For each
published package with a `screenshots:` field it checks pub.dev's rules
(the section "What pub.dev does") and D6's budget: at most 10 entries; each path
normalised, unique, existing, not under a directory the package's
`.pubignore` excludes, of an allowed extension, at most 1 MB; the total at
most 4 MB; each description 10–160 characters after trimming; and every
`raw.githubusercontent.com` image URL in the package's README pointing at a
file listed in `screenshots:` under the package's current version's tag.
Named mutations (each must turn a test red): an eleventh entry; a 9- and a
161-character description; a path under `test/`; a missing file; a
`./`-prefixed path; a README URL on `main` or on the previous version's
tag.

## D8. README snippets are analysed: `tool/readme_probe`

A new workspace member `tool/readme_probe` (Flutter, `publish_to:
none`; beside `tool/ci`, not inside it, so no workspace member nests in another) with one file per README, each importing only the barrels its README
names: `lib/engine.dart` (`jet_cad_2d`, `vector_math`), `lib/renderer.dart`
(`jet_cad_2d_flutter`, `flutter/widgets`), `lib/planner.dart`
(`jet_cad_floor_plan`, `flutter/material`). Each README `dart` block occurs
in its file, white space collapsed, inside whatever function or class makes
it compile. `tool/ci/check_readmes.dart` reuses `lib/guide.dart`'s
`fencedBlocks` and `collapse`: every `dart` block of each package README is
in its probe file, and the planner's `yaml` block (the font family) is in
the host probe's `pubspec.yaml.in`. A README with no code block where the
probe expects one is red. CI's `ci-tools` job runs `check_readmes.dart`
and `flutter analyze` in `tool/readme_probe`. Named mutations: a README snippet's
identifier changed (the check red); a probe's barrel import dropped or an
API name misspelt (analyze red).

## Risks

- **MaterialIcons in `flutter test`** may not load from the manifest: D4's
  fallback; if neither works, the plan's first task stops and asks.
- **Scenes using `editor.dart`** (`startupPlan`) depend on an API outside
  semver; the generator is unpublished, so a change breaks only the
  generator, in CI.
- **Tag-pinned image URLs** are broken on GitHub until each tag is pushed
  (D6, D11).
- **Archive growth** of up to 4 MB per package, for every download; D6's
  budget and the recorded sizes bound it.
