# Openings (sub-project 08) — implementation plan

> **For agentic workers:** executed task by task, subagent-driven: a fresh
> implementer per task and an independent reviewer per task, then a final
> whole-branch review. Steps use checkbox (`- [ ]`) syntax.

**Goal:** doors, windows and gaps hosted in walls. An opening is its own
parametric object. It stores its host wall's handle and a position along
the host's centreline. It cuts the host's band and centreline, and draws
its own symbol. It moves with its wall and is deleted with it. It stays out
of the wall's corners and out of other walls' T butts and crossings.

**What ships:**
- three tools, Door (D), Window (N) and Gap (G), each placing an opening
  with one click;
- an Opening section in the Selection panel, and a slide grip;
- wall end grips that keep openings where they are;
- the sample plan rebuilt with 07 walls and 08 openings.

**Architecture:**
- **The engine** (06's mechanism) gains:
  - explicit **references** between parametric objects;
  - a closure that follows them with one extra hop;
  - a per-type **reference policy** (`cascade` or `orphan`), with the
    cascade run inside the edit;
  - a refusal of dangling references on edit, and their report on load.

  All of it is generic.
- **The render layer** gains one method on its object-grip seam
  (`ObjectGripProvider.movable`), which move, rotate, the rotation grip and
  the hover cursor honour. It also gains one overridable getter on
  `PlacementTool` (Ruling 08-14).
- **The app** gains:
  - `OpeningParams` and `OpeningType`;
  - pure opening geometry: the host frame, obstacles, stretches, cuts,
    pieces and symbols;
  - a wall band split into pieces, with a split centreline;
  - a position rewrite on end drags;
  - the three tools;
  - a composite grip provider with the slide grip;
  - the Opening section;
  - the rebuilt sample plan.

**Tech stack:** Dart, Flutter 3.47.2; `package:test`, `flutter_test`,
`vector_math`. No new dependency.

## Rulings made here rather than left to an implementer

Each ruling says what the plan does, why, and what it costs if wrong.
Rulings marked **(spec amended)** are written into the spec in Task 16.

- **Ruling 08-1 — test identifiers.** The spec's identifiers are kept,
  with these exceptions and additions:
  - **renamed:** the spec's `EG1`–`EG4` become **`EP1`–`EP4`**, because 07's
    `apps/floor_planner/test/wall_grips_test.dart` already has `EG1`–`EG5`;
  - **render-layer `movable` tests:** `MV1`–`MV4`;
  - **the plan's own new tests:**
    - `HF1`–`HF7`: the host frame;
    - `CS6`, `CS7`: the cascade on detach and on re-parent;
    - `OD1`: diagnostics, only the accepted cases;
    - `DF1`: from scratch against incremental;
    - `RC3`: app-level timing;
    - `EP5`: a shortened wall;
    - `OT5`: the snap marker;
    - `SP6`: the sample plan's byte identity.

  08's app tests go into **new files** (`opening_*_test.dart`). **07's six
  wall test files are not edited**; Task 15 checks it with a diff. The
  only earlier tests this plan edits are `startup_plan_test.dart` and
  three sample-plan tests in `planner_shell_test.dart` (Task 13). **Cost:**
  none.
- **Ruling 08-2 — the engine's test-only clients** (the spec's Files: a
  host, a `cascade` referrer, an `orphan` referrer). They live in
  `packages/jet_cad_2d/test/parametric/support/clients.dart` and are
  registered in `testCatalog()`. The names avoid 06's existing `Hinge`
  client:
  - **`Post`**: a `RectParams` that `rectOf` recognises. `generate` is
    `clippedRect` (so it reads its neighbours) plus one tick LINE per
    referrer, read through `view.referrers(self)` and each referrer's
    `Pin.offset`. A Post reads its referrers as a wall reads its openings.
    `reach` is `rectReach`. `diagnose` reports its referrers (for `RF1`).
  - **`Pin(host, offset, {region})`** (default policy, `cascade`):
    - `reach` is `Aabb2.empty()`; `references` is `[host]`;
    - when the host is a Post, `generate` emits the host's **clipped**
      bottom edge, host-local → world → own local. That makes the two-hop
      shape: the edge depends on the host's neighbours;
    - when the host is a Pin, it emits one LINE from its own origin to the
      host's origin;
    - otherwise it emits nothing;
    - `region: true` adds one region, to exercise the cascade's fill-skip
      rule.
  - **`Tag(host)`** (policy `orphan`, from Task 2): like `Pin`, but with no
    live Post it emits one fixed "orphan marker" LINE at its own origin.
  - Each client counts its `generate` calls per handle in a static map that
    the tests reset.

  **Cost:** none. 07's Ruling 07-8 reasoning applies: engine tests cannot
  import the app.
- **Ruling 08-3 — one `references` call per live object per survey.**
  - `_Registration.referencesOf(t, h)` increments the library-level
    `@visibleForTesting int debugReferenceCalls`. The library never resets
    it.
  - The survey keeps the **declared** list from that one call per object
    (`_Survey.declared`), next to the filtered `references` and
    `referrers`. D5's check (Task 2) and `diagnostics()`'s
    `parametric.dangling` and `parametric.orphan` read `declared` and
    never call `references` again.

  `RC1` pins exactly `2 × n` calls for an edit that touches no object.
  **Cost if wrong:** none: a second call site would turn `RC1` red.
- **Ruling 08-4 — liveness for the cascade.**
  - "Stopped being a live object" (D4) is decided only for handles that
    had referrers before the edit (`before.referrers.keys`). The test is
    06's `_isObject` on the current tree: node present, root-level group,
    registered component. That covers a removed node, a detached
    component and a re-parented group alike.
  - Each round costs O(referents), never a scan of every object.
  - A doomed referrer is itself no longer an object after its removal, so
    the next round picks up its own `cascade` referrers without any extra
    bookkeeping.

  **Cost:** none.
- **Ruling 08-5 — where D5's check sits.** Inside 06's `try`, after the
  seeds are computed and before the "no seeds" early return and the
  closure. For each seed that is a live object in `after` with policy
  `cascade`, every `declared` handle must be in `after.objects`; the first
  failure in ascending (seed, referent) order throws
  `DanglingReferenceError(seed, referent)`. The `catch` already applies
  `r.inverse`, which includes the cascade's (D4 step 5). **Cost:** none.
- **Ruling 08-6 — where D2's cost is measured.**
  - `RC1` and `RC2` are engine tests with the test clients, as the spec's
    Files section says (`reference_cost_test.dart`).
  - The spec's open question 13 says RC2's wall-move timing "includes"
    each opening recomputing its host's joints. Test clients have no
    joints, so **`RC3`** (Task 7) repeats 06's NC4 method in the app, with
    real walls, one opening each. It is printed, not asserted, and the
    results note records it next to NC4 and RC2.

  **Cost:** one printed test.
- **Ruling 08-7 — task order and placeholders.** The spec's diagnostics
  (D17, app half) come in **Task 5**, before the UI, not near the end.
  `OG2`–`OG6` assert them, and the UI tasks do not need them.
  `OpeningType` is registered in Task 4 with `generate` returning
  `const []` until Task 6 and `diagnose` returning `const []` until Task 5.
  An opening between those tasks is a childless group. Every task still
  ends green. **Cost:** none.
- **Ruling 08-8 — the geometry's shape: one function, two adapters.**
  D7 says one function, called by the wall and by each opening, so both
  get the same bits.
  - `opening_geometry.dart` holds pure functions over plain inputs:
    - `hostFrameOf(WorldWall host, List<WorldWall> walls)`: the frame in
      the host's group-local space;
    - `obstaclesOf`, `stretchesOf`, `placeCut`, `mergeCuts`, `overlaps`,
      `piecesOf`, `centrelinePieces`;
    - the symbols.
  - Two thin adapters build `walls`:
    - **the view adapter**, used inside a regeneration, takes the host's
      `view.neighbours(host)` carrying `WallParams`;
    - **the document adapter**, used by the tools, the grips and the panel
      (Task 9), takes every live wall object in ascending handle order.
      `classify`, `cap` and the obstacle tests ignore a wall that does not
      join, so the extra walls change nothing.

  `HF7` (Task 9) pins that the two adapters agree **bit for bit** on `OG9`'s
  random plans. **Cost if wrong:** `HF7` turns red, and the fix is to filter
  the document adapter by the engine's reach-overlap predicate.
- **Ruling 08-9 — the oracles and their home.**
  `apps/floor_planner/test/support/opening_fixture.dart` ports the spike's
  `support.dart` (`addOpening`, `worldPieces`, `worldPoints`,
  `oracleFrame`, `gapRect`, `uncutOutline`, `tiling`, `violations`,
  `allTriangulate`, `doorOracle`) and adds:
  - **`oracleObstacles(doc, wall)`**:
    - a T's interval is the `u`-range of the stem's **stored** vertices
      (in the twin document) that lie inside the host's band. That is a
      differential against 07's own T cap;
    - an X's interval is the `u`-range of the four crossings of the two
      walls' oracle faces, by `oracleMeet`;
  - **`oracleSpan(doc, wall)`**: the spike's span from the twin's stored
    outline;
  - **`oracleCut(doc, opening)`**: an independent clamp into the stretches
    that those two give.

  Nothing in the fixture calls `opening_geometry.dart`. **Cost:** none.
- **Ruling 08-10 — `EP1`'s fixture.** The spec's `EG1` says every opening
  stays put in world, "joined walls' openings included". For a joined
  wall at an angle that is false: the joined wall swings about its unmoved
  end, and D13 keeps its openings' distance from that end. So `EP1` uses
  two **collinear walls back to back that share their starts** at the
  dragged node, and drags along their common line. Both walls' openings
  are then rewritten, and all of them stay put. An L's joined wall is
  covered by `EP3`. **Cost:** none.
- **Ruling 08-11 — the band cache, factored.**
  - 07's cache moves from `wall_tool.dart` into
    `apps/floor_planner/lib/parametric/wall_bands.dart` (`WallBands`). It
    now also stores each wall's handle, and `hostAt(x, y)` returns the
    lowest-handle wall whose band contains the point.
  - The shell owns **one** instance and passes it to the Wall tool and the
    three opening tools. `WallTool` gains an optional `bands:` parameter
    that defaults to its own instance, so 07's tests are untouched, and it
    keeps its own `debugBandScans` counter.
  - **The opening tools' host scan is not gated on object snap (F3).**
    Finding the host is not a snap; with F3 off the tools would otherwise
    do nothing. F3 gates only 07's band joining and D15's edge snaps.

  **Cost if wrong:** with F3 off, D, N and G still place on walls.
- **Ruling 08-12 — the per-hover cost.** The spec (D14) says a hover scan
  "scans nothing when no wall is near (07 `WT12`'s bar)". 07's cache has no
  spatial cull, and 07's early return exists only because the Wall tool
  has no rubber band without a chain. An opening tool must find its host
  on every move. So the hover runs 07's O(walls) scan over cached doubles,
  which allocates nothing in steady state, and "scans nothing" is read as
  **builds no preview and computes no frame**. `OT4` measures the
  per-hover cost at 600 walls with `WT12`'s method, and pins the
  no-preview path with counters. **Cost if wrong:** a large plan's hover is
  a linear scan. A culled scan through the spatial index is the follow-up.
- **Ruling 08-13 — the tool's frame cache.** `OpeningTool` caches the
  hovered host's frame, stretches and the host's other openings' cuts. It
  rebuilds them only when the hovered host changes or the document
  reports a change (`doc.changes`, as `WallBands` does). It also rebuilds
  them at every click. A pointer move over the same host costs a
  projection, a placement and the preview's few points. **Cost:** none.
- **Ruling 08-14 — the raw point and the snap marker.**
  - `PlacementTool` hands `accept` the **resolved** point only, but D14
    needs the **raw** click for the host and the swing side. `OpeningTool`
    overrides `onPointerDown` to record `e.world`, then calls `super`.
  - D15 wants the snap marker at the projected point, and `PlacementTool`
    paints it at its private hover point. `PlacementTool` gains
    `@protected Vector2 get markerPoint => hoverPoint;`, which
    `paintOverlay` uses. Every other tool is unchanged; `OpeningTool`
    returns its projected point.

  **Cost:** one render-layer getter (**spec amended**, D15 and the
  Architecture's render-layer list).
- **Ruling 08-15 — the slide grip's snapping.**
  - `ObjectGripProvider.drag` receives the point the select tool has
    already resolved through the chain (grid and object snap). So the
    grip's edge snaps (D15) are evaluated on that resolved point,
    projected, and not on the raw point as a tool's `selfSnap` is.
  - The composite takes `double? Function() edgeAperture`. The shell
    passes `() => _snap.objectSnap ? kSnapAperturePixels /
    _camera.value.scale : null`, and `null` turns edge snaps off.

  **Cost if wrong:** near its own old edges, the chain can pull a slid
  opening onto them. The preview shows it (**spec amended**, D15).
- **Ruling 08-16 — `movable`, everywhere the select tool starts a move or
  a rotate.**
  - `GripDrag.move` and `GripDrag.rotate` take `{ObjectGripProvider?
    objects}` and skip a root-level group that it calls immovable.
  - `SelectTool` passes `ctx.grips?.objects` at all four call sites
    (`select_tool.dart:216, 228, 252, 274`).
  - `GripCache.rotatable` needs at least one movable key.
  - `hitsRotationGrip` returns false when not `rotatable`: it reads `_box`
    directly today (`grip_cache.dart:274`).
  - `_hoverAt` shows no move cursor over an immovable selected key.
  - `WallGrips.movable` and the test fake answer true. The composite
    answers false for an opening and true for everything else.

  **Amended at execution (Plan 08):** the composite now asks the
  dispatched provider, so `OpeningGrips.movable` holds the one rule:
  false for an opening, true otherwise. A group that is neither a wall
  nor an opening is movable (Task 14's F2; `SG6` pins the default).

  **Cost:** none.
- **Ruling 08-17 — the Opening section's wiring.** `SelectionPanel` gains:
  - `openingTools: Map<OpeningKind, Tool>?`;
  - `openingSettings: Map<OpeningKind, ValueNotifier<OpeningSettings>>?`.

  Both are owned by the shell. `OpeningSettings` holds `width` only; the
  defaults are 900, 1200 and 900. In tool mode the section edits the
  active tool's settings, even when an opening is selected. The panel's
  existing `_toolSettings` sentinel stays the Wall tool's. Each opening
  tool's settings target is a distinct sentinel handle, or the kind, at
  the implementer's choice. **Cost:** none.

  **Cost:** none.
