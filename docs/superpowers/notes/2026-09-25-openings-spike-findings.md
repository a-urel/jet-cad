**Date:** 2026-09-25.

**Status:** throwaway. The branch is never merged; this note is its only
output. It is an input to 08's spec, not a design.
**Where it ran:** a Linux x86_64 cloud container, the workspace's Flutter
and Dart (`/root/flutter/bin`), not the human's macOS machine. No test pins
a hash of rotated geometry (07's platform note): every byte comparison is

**The human's decisions the spike worked under:**

| Question | Decision |
|---|---|
| Where the symbol comes from | Generated by the opening's own regeneration; no library |
| How an opening reaches its wall | Explicit engine **references**: a type declares the handles its parameters reference |
| What an opening is | Its own root-level object (a group and a component) |
| How the wall is cut | Its band splits into **pieces**, one `Generated.region` each; a 1-D split along the straight wall |
| An opening that does not fit the straight part | Keeps its stored position, is **drawn clamped**; if the span is shorter than its width, the wall is uncut and only the symbol shows; `diagnose` names it |
| Deleting a wall | **Cascades** to its openings, in the engine, generically, one undo step |
| Overlapping openings | Allowed; the wall cuts the union; `diagnose` names them |
| Types | Single-leaf door (width, hinge end, swing side), window (width), gap (width); each carries its host's handle and a position along the host's centreline |
| Colours | Symbols ByLayer on layer 0; walls stay concrete black |

## The rules that survived

### 1. The closure: references, and one extra hop

The brief proposed: for each seed, add the objects it references and the
objects that reference it. **That failed first.** Q1d: wall A 200 centre
runs into a node that B 115 left runs out of, at 67°; a door in A is stored
at 2,700 so that it is drawn clamped against A's mitre. Swinging B's far end
changes A's mitre, so A's straight span, so where the door is drawn — but
the door is neither B's referrer nor B's referent:

```
Q1d the two-hop case: B joined to A moves; A's door, clamped at A's mitre, follows [E]
  Expected: empty
    Actual: [4000]
  the door is two hops from B
```

A referrer reads more than its referent's parameters: it reads the
referent's **joints**, which read the referent's spatial neighbours. The
rule that survived:

```
core    = seeds ∪ neighbours_before(seeds) ∪ neighbours_after(seeds)
        ∪ references_before(seeds) ∪ references_after(seeds)
closure = core ∪ referrers_before(core) ∪ referrers_after(core)
```

It is closed for this client: a door reads its own parameters, its host's
and the host's wall neighbours'; a wall reads its own, its wall neighbours'
and its openings'. Every change to any of those lands a seed whose one-hop
set holds the door's host, and the door is that host's referrer. The other
direction needs nothing more: B never reads A's openings, so editing A's
door never needs B (Q1e: `drift()` empty, B's children unchanged byte for
byte).

### 2. The cascade: after the guard, before the after-survey

`_cascade` runs right after 06 D6's guard and before `after = _survey(…)`.
It removes each doomed referrer's leaves (a fill whose boundary also goes is
skipped, as the select tool does) and then its node, as one
`CompoundCommand`, repeats until nothing more is doomed, and folds the
removals into `r`: `r.inverse` becomes `[cascade inverses reversed…,
inner's inverse]`. Everything after it is 06's code unchanged. The
after-survey never sees a doomed referrer; `lost` picks it up by itself
(its node is gone), so 06 D8's cleanup detaches its component and it seeds
the closure like any deleted object.

**Why not later.** Without the cascade (mutant M-08f0) the orphaned door is
still in the closure, as a before-referrer of the deleted wall. Its
`generate` finds no host and returns nothing, so the planner strips its
children and leaves a childless group behind — 06's ghost:
`Expected: null Actual: GroupNode:<GroupNode(FA0, 0 children)>`. A cascade
computed from the after-survey would plan exactly that removal and then
remove the node under it.

### 3. The straight span and the pieces

- **The straight span** of a wall is `[uS, uE]`, `u` measured from `start`
  along the centreline in the wall's own local space: `uS` is the largest
  `u` of any **start-cap** vertex, `uE` the smallest of any **end-cap**
  vertex. The caps are 07's own (`capsOf` is `outline` with its two caps
  kept apart), including the lobe walk, the T butt, the clamp feet and
  07's local-space fallback (final review I1). Between `uS` and `uE` both
  faces are plain offsets, whatever the joint.
- **Cuts:** an opening's `[c − w/2, c + w/2]`, shifted into `[uS, uE]` when
  it pokes past; no cut when `w > uE − uS`. Cuts sorted and merged when the
  next starts within `wallJoin.linear` of the previous end.
- **Pieces**, anticlockwise like 07's ring: the start piece is `[R(a₀),
  L(a₀)] + start cap`; each middle piece `[R(aᵢ₊₁), L(aᵢ₊₁), L(bᵢ),
  R(bᵢ)]`; the end piece `end cap + [L(bₙ), R(bₙ)]`. A piece no longer
  than `wallJoin.linear` along the centreline is dropped (an opening
  clamped against a square cap). The jambs are the pieces' own edges: no
  jamb child is needed.

**What failed first.** A cut clamped onto the span lands exactly on a cap's
face vertex. The face point recomputed there differs from that vertex by
rounding (~1e-10), and the near duplicate makes 07's triangulation check
refuse the region: the **edit throws `ArgumentError` and is rolled back**.
First seen at trial 3 of the random run below; measured with the fix
removed (mutant M-snap): **66 of 1,244 random openings refused (5.3%)**.
The rule that survived: within `wallJoin.linear` of the cap's face vertex,
that vertex is the cut's corner (the recomputed point is left out). 0
refused after.

**The oracle.** 20,000 points uniform in the box of the uncut band, grown by
50 mm. Every point inside the uncut band must be in exactly one piece **xor**
in a gap rectangle (`[a, b]` face to face, from an independent frame
written out from the stored parameters); no point outside the band may be
in a piece or a gap; no point is in two pieces. Five counters: `overlap`,
`hole`, `pieceInGap`, `pieceOutside`, `gapOutside`. Plus: every stored piece
has triangles, and no vertex of the uncut band lies strictly inside a gap
(the gap is in the straight part). Expected gaps come from an independent
clamp against an oracle span read off the uncut band's vertices.

**The oracle's own first failure.** The uncut band was first taken from 07's
`outline` in world. At trial 38 it disagreed with the pieces (`hole: 93,
pieceInGap: 55`): a straight-through step whose lobe cap passes exactly
through a vertex is simple in world and not in local space, so 07 stores the
wall's free rectangle there, and the frame followed 07. The oracle that
survived is **differential**: the uncut band is what 07 **stores** for the
same wall in a twin document (saved, reloaded, every opening deleted).

## Findings nobody asked about

1. **The wall's centreline crosses every doorway.** 07 D3 generates it in
   `kWallColor`, invisible inside the band; in a gap it is a black line
   across the opening, on every paper (`r1_l_and_t.png`,
   `r2_blueprint_wall.png`). For a left- or right-justified wall it runs
   along a face. It also makes the doorway pick the wall (Q6).
2. **A T stem can land in a doorway.** The straight span is judged from the
   wall's own caps; another wall's T butt or X crossing in the middle of
   the wall is not an obstacle. `r1_zoom_t_door.png`: a stem ends on the
   near face line, in the middle of a door's gap, its centreline stub
   running on to the through wall's centreline. 07 D6's recorded risk
   (a neighbour's overlapping fill covering a cut near a joint) is the
   same thing at a node.
3. **A bare `RemoveNodeCommand` of a wall's node orphans the wall's own
   leaves** (pre-existing in 06: D6 allows a node removal, and only the
   select tool's compound removes the leaves). Q2c: node gone, `A children
   [1301, 1302, 1303, 4001, 4002, 4101, 4102]` left with a dead owner,
   `drift []`. The spike's cascade removes a referrer's leaves itself, so
   it is stricter for referrers than 06 is for the object deleted.
4. **Position from the start moves doors when the start moves.** Q5b: the
   wall's start pulled back 500 mm along the wall: `the door moved
   500.0000000004543 mm in world`. 07's end grip on the start does this.
   Hinge end and swing side are relative to the host's direction too.
5. **A handle is now stored in a component** (`OpeningParams.host`). The
   component is opaque to the document, so any future handle remap (paste,
   import, block explode, merging files) must learn it, through
   `references` or a sibling hook.
6. **`opening.overlap` is reported twice per pair** (once by each opening):
   Q3f's 926 entries. Report once, by the lower handle.
7. **Every opening recomputes its host's joints.** `hostFrame` runs
   `classify`/`cap` on the host's neighbours once for the wall and once per
   opening in the same plan. Not measured.
8. **References cost O(n) per survey**, twice per edit, including a plain
   line drawn in a plan of walls (07 D10 made neighbours free for such an
   edit; references are not). Not measured.

## Consequences for 10 (rooms) and 09 (library)

- **10:** the pieces break the faces at every doorway, so rooms must be
  derived from the **uncut** faces and centrelines (07's advice stands),
  or they leak through doorways. **The generic cascade is wrong for
  rooms:** a room that referenced its walls would be deleted with any one
  of them. The reference mechanism needs a **per-type policy** (cascade,
  or orphan and diagnose) before 10. A room reading its walls' joints is
  exactly rule 1's two-hop case again; the closure rule covers it only if
  rooms are referrers.
- **09:** a library symbol cannot be placed by an opening's regeneration
  today: `_plan` generates leaves only, never an `InstanceNode`. Swapping
  generated symbols for library ones needs the planner to generate
  instances (their own draw-order and D6 questions). An opening inside a
  block instance is not regenerated at all (06 D5: root-level only).

## Open decisions for the spec

Options cheapest first.

1. **The centreline across the gap** (finding 1).
   1. Accept it; it reads as a threshold line. Q6's doorway pick selects
      the wall.
   2. Split the centreline with the band: one open polyline per piece.
      Variable child count again, but black on black, so no visible draw
      order.
   3. Stop generating the centreline (07 D3 generated it for picking and
      snapping; the fill picks, and 07's Wall tool band-joins from a cache
      of world walls, not the entity).
2. **The no-fit symbol and draw order** (Q4).
   1. Accept: invisible on light paper, visible on Blueprint only.
   2. A no-fit opening draws no symbol, only its `opening.nofit`.
   3. A no-fit opening draws its symbol outside the band (for example at
      the face), keeping "a symbol never overlaps a piece".
   4. A per-object draw pass (06 D12's question): the general fix, at the
      painter's cost.
3. **Obstacles in the straight part** (finding 2).
   1. Accept, and `diagnose` an opening whose gap holds another wall's T
      butt or crossing.
   2. Treat those footprints as obstacles: the span becomes several
      intervals and the clamp picks one.
   3. Forbid: such an opening is no-fit.
4. **What the position is measured from** (finding 4).
   1. The distance from the start, as spiked; the start grip moves doors.
   2. The same, and the start grip's command also rewrites its openings'
      positions (the grip provider must learn about referrers).
   3. A fraction of the length: every end drag moves every door.
5. **The gap opening's selectability** (Q6).
   1. Two jamb lines (or one threshold line) as its children.
   2. Accept that it is deleted only through its wall.
6. **The cascade's policy** (10).
   1. Generic cascade, as spiked; revisit at 10.
   2. A per-type policy on `ParametricType` now: `cascade` or `orphan`.
7. **Overlap reporting** (finding 6): once per pair, by the lower handle.
8. **M-08a** (the position stored as world coordinates) was **not fired**:
   it needs a different parameter type, not a one-line mutant. The spec
   should say how it is fired, or record it as structural.
