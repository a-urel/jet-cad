## Criterion 17 — the miss, what actually caused it, and what it means for 3g

**The cause, found by running the process rather than reading the API.** The
probe's own diagnostic first read only two facts —
`Service.controlWebServer(enable: true)`'s `serverUri` came back `null`, and
`Service.getIsolateId(Isolate.current)` resolved normally — and the first
write-up chose a branch of its own disjunction ("the web server never starts")
that neither fact actually separated from its alternative. The task review
looked at the launched process instead:

```
flutter_tester --disable-vm-service --enable-checked-mode ...
```

**`flutter test` launches `flutter_tester` with `--disable-vm-service`.** The
VM service is switched off at the process boundary, before any in-isolate call
runs. `AllocationMeter`'s mechanism — start the service at runtime from inside
the isolate under test, with no launch flag — cannot work there, not because
the platform lacks the capability, but because the harness that runs the test
disables it before the test's own code executes.

**What Plan 3g now knows, before it starts.** 3g's central risk — a
lazily-populated picture cache allocating on a frame-path cache miss,
invisible to `paint_allocation_test.dart`'s buffer-capacity read (trap 5) —
**cannot be gated by a frame-path allocation profile in `jet_cad_2d_flutter`**,
because the one mechanism this plan built and proved under plain `dart test`
does not carry into `flutter test` at all. 3g needs a **command-time
assertion** instead: the same shape that actually proved fills are
materialised eagerly in Plan 3e (`the triangulation is materialised by the
command, not by a draw`), after Plan 3e's own allocation gate stayed green
through the exact mutation that should have broken it. A buffer-capacity read
answers "did the vertex buffer grow"; it cannot answer "did something get
allocated and dropped on the general heap on a miss."

**What is explicitly withdrawn, and what stays open.** The ledger's first pass
at this finding went further than the evidence and stated "no retry would
help." That is withdrawn. The cause is a **launch flag**
(`--disable-vm-service`), not an intrinsic platform limitation — so a
flag-based route is **plausible and unexplored**, not impossible:
`flutter test --start-paused`, or any invocation that stops passing
`--disable-vm-service`, was never tried. It would still not serve an
**always-on** gate, because the flag is supplied by `flutter test` itself, not
by anything this repository controls per-test-run — so even if such a route
exists, it could not be the standing CI gate 3g would want. It could still be
a one-off diagnostic tool for someone chasing an allocation regression by
hand, which is why it is recorded as unexplored rather than closed.

**The revert was complete and independently confirmed.** The file move, the
`lib/testing.dart` export, the `pubspec.yaml` promotion of `vm_service` to
`dependencies`, the three re-pointed imports, and the probe test file were all
reverted; `git status --short` after the revert showed a clean tree, and both
the task reviewer and a re-reviewer verified the tree byte-identical to
`b1e9ec1` (the last commit before Task 7 began). Section 3 of the plan is
dropped. No commit exists for Task 7.

## The plan's own recurring failure mode

This is written up because it is the most useful thing this plan produces, not
despite that it is uncomfortable.

**Three times in this plan, a stated cause was written down more strongly than
the evidence behind it — and each time, the mistake was caught by someone
running something, not by someone reading it, even though this plan alone had
three rounds of external spec review before a single line of implementation
code was written.**

1. **The spec's own defect 4, present tense, false.** It stated "no test in
   that file ever pushed past 512 distinct metrics keys" about
   `flutter_text_measurer_test.dart`. That was true of the file as it stood
   before Plan 3f's own remedy commit `645b027`, which is exactly the test
   that closes the metrics half of the same gap — a bare measurer swept 513
   distinct strings through `measure()` and pinned `metricsEvictionCount == 0`.
   Three rounds of independent spec review read past that sentence because
   none of them was pointed at it specifically. It surfaced only when Task 5's
   own implementer wrote a comment restating the spec's claim, the controller
   ran the file's own mutation transcript against it, and the transcript
   contradicted the comment it was meant to justify. Fixed in `e39f295`
   (fix round 1/5): the comment was narrowed to what the new file actually
   adds (the paragraph-cache half), and the false present-tense claim about
   the sibling file was removed.
2. **The ledger's own "no retry would help," about the Task 7 probe.** Recorded
   above under Criterion 17 — the controller's own ledger entry asserted an
   implication ("no retry would help") that the two measured facts
   (`serverUri: null`, `getIsolateId` resolving) never separated from its
   alternative. The Task 7 reviewer found the actual cause by reading the
   launched process's command line, not by re-reading the same two facts
   harder.
3. **The Task 7 report's own first write-up**, "the web server never comes
   into existence" — the same honest disjunction chosen down to one branch,
   with no evidence distinguishing it from the other, that the ledger then
   repeated and extended. The correction (`Ruling T7-B`) replaced the
   reasoning, kept the superseded version visible in the ledger rather than
   rewriting it away, and withdrew the strengthened implication that had been
   built on top of it.

The common shape: an engineer (in one case, the plan's own author) has two
facts, notices a disjunction, and writes down one branch of it as if it were
the only one — because the chosen branch is the one that makes a clean
sentence. Reading catches typos and missing cases; it does not catch a
plausible sentence sitting on evidence that never actually chose between two
explanations. What catches it is running the thing the sentence claims to
describe — a mutation transcript, a process listing — and checking that what
comes back actually rules out the alternative.

## Three plan premises corrected mid-flight

Recorded here, in one place, so the next plan's author does not repeat their
shape. Full rulings are in `progress.md`.

1. **Layer 0 already has a seeded record.** Task 2's fixture assumed layer 0
   had no record and could be freely added; `DraftDocument.empty()` seeds one
   at `tables.dart:509-516` via `DocumentTables.standard()`. The plan author's
   own check had grepped only `draft_document.dart`. Fixed by having the
   shared `addLayer` test helper remove-before-add, following the existing
   precedent at `test/index/query_filter_test.dart:381`. Recorded in the
   ledger as Ruling T2-A, with a deferred minor: the unconditional
   remove-before-add would silently mask a genuine duplicate-handle defect in
   a future test in the same file that meant to add a *new* layer, scoped to
   one test file and carried to final triage rather than fixed here.
2. **Task 1's "the pre-existing suite will not move."** Three pre-existing
   tests moved as a direct, mechanical consequence of the schema bump and the
   new `InstanceNode` fields: one pins `kSchemaVersion == 5` by literal
   (`json_codec_test.dart:484-488`), and two are FNV-1a fingerprints over the
   generated corpus (`generate_document_test.dart:56-59,233-236`) that shift
   whenever the serialised shape changes — as their own comments already
   record happening twice before, at the two prior schema bumps. Authorised
   for re-baseline (Ruling T1-A) only after confirming the diff never touches
   the generator and that all structural sibling assertions in the same file
   stayed green — the discriminator between a benign shape change and a real
   RNG-order regression.
3. **Task 2's "eight tests, all FAIL."** Six failed; two passed pre-change.
   The two `kLineweightDefault` tests expect the inherited lineweight (`25`),
   and the pre-change `contextFor` already returns `25` because it ignores the
   instance entirely — they are regression guards for a capability that did
   not yet exist, not red-green drivers. Corrected in the ledger before Task 2
   was dispatched (Ruling F2), so the implementer was not left to trust a
   false "all fail" and edit a correct test to make it fail.

## What this plan did not close

- **Permitted divergence 5** — overlapping translucent strokes on a triangle
  soup. Untouched by this plan, exactly as scoped; still unexercised by any
  fixture in the repository.
- **The malformed-layer asymmetry**, mirrored rather than fixed (spec's
  accepted gap 2). A layer whose *colour* is itself BYLAYER or BYBLOCK is
  rejected by `_concreteLayerColor`; a layer whose *linetype*, *lineweight* or
  *transparency* is one of those sentinels is not checked at all. Decision 2
  mirrors that asymmetry onto instance resolution rather than fixing it, so an
  INSERT and an entity always agree with each other — even though both may be
  wrong in the same way. Fixing the entity side is a separate change with its
  own blast radius, out of this plan's scope.
- **An INSERT's own ATTRIBs do not see the style the INSERT now imposes.**
  `container_index.dart:207-224` folds an instance's own leaves — its
  ATTRIBs — into the *enclosing* container's leaf list, so `DraftPainter`
  draws them with the enclosing context rather than `contextFor(instance,
  ctx)`; `reference_walk.dart:88-99` mirrors the same fold, which is why the
  differential suite cannot see it — painter and oracle agree with each
  other, both from the enclosing context. In DXF an ATTRIB is a sub-entity of
  its INSERT, so a BYBLOCK value on it should resolve against the INSERT, not
  against whatever placed the INSERT. **This is not a regression introduced
  by this plan** — it was already true for `color` and `layer`, the only two
  style fields `InstanceNode` carried before this plan — but this plan is
  what made INSERT style mean anything beyond those two fields, and it
  quadruples the affected surface (`lineweight`, `transparency`, `linetype`,
  `linetypeScale`, on top of `color` and `layer`). No code changed for this;
  it is recorded as a gap, not fixed here.
- **Ruling 4's single permitted `kParagraphCacheLimit` raise is still
  unspent**, with its measured **3,876** distinct visible paragraph keys still
  recorded beside it (Plan 3f Task 8). It can only be spent once; whether to
  spend it on Plan 3f's own missed rows or hold it for 3g remains a human
  decision, not a plan's.
- **The `TextKeySink` move is currently inert.** The spec justified moving it
  from `test/rig/rig_support.dart` to `test/support/` as "one definition, four
  readers"; that count was wrong — it counted the class's own declaration
  site in `rig_support.dart` as a reader — and neither new invariants file
  imports it (`text_cache_invariants_test.dart` says outright that a
  `TextKeySink` cannot carry criterion 12). The move itself is kept: the class
  is better placed in `test/support/` than declared inside a rig file. But
  today both of its real readers, `paint_microbench_test.dart` and
  `flutter_text_measurer_test.dart`, still reach it through
  `rig_support.dart`'s re-export — no import path changed, so the move has
  not yet paid for itself.
- **Criterion 17, in full** — see above. The instrument does not work under
  `flutter test`; the mechanism (in-isolate runtime service start) is
  incompatible with `flutter_tester`'s `--disable-vm-service` launch flag; a
  flag-based alternative is plausible and unexplored, and could not serve an
  always-on gate even if it worked, since the flag is not controlled per-test
  by anything in this repository.
