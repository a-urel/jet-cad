Task 5 deviations and decisions:
1. The plan gives `CanvasDrawSink` no test at all and leaves its draw calls as
   a one-line sketch. It is the only place the project touches `dart:ui`, so it
   is covered by a spy `Canvas` (`noSuchMethod`, snapshotting the reused

3. `draw_sink.dart` uses the engine's `listEquals`, not Flutter's, and imports

   `dart:test` suite.
4. `BeginResidualOp` compares its `Transform2` field by field, exactly.
   `Transform2` deliberately has no `operator ==`. OPEN QUESTION for Task 11:
   if the cached and uncached painters compose the same residual in different
   orders, exact equality can differ in the last bit. The oracle may need a
   tolerant comparison for this one op; every other op compares exact.
Mutation check: transposing the affine, dropping the residual division from

Task 6: complete. `DraftPainter`'s root-leaf pass. 46 tests in the Flutter
package, 619 in the engine, both analyze and format clean.

**The reference implementation is wrong, and the plan's own first test catches
it.** Task 6's `_drawLeaf` composes `camera . leafTransform . translate(origin)`
while `_emit` subtracts `localOrigin = leafTransform⁻¹(origin)` from every
point. Those two agree only when `leafTransform` is the identity. For
`chain(p - localOrigin)` to equal `camera(leafTransform(p))`, the chain's
rebase translation must be `localOrigin`, not the world `origin`. Implemented
with `localOrigin`; mutating it back to the reference fails both group tests.

Other Task 6 deviations:
1. A singular `leafTransform` — a group scaled to zero on an axis — makes
   `invert()` throw, per leaf per frame. Such a leaf now skips rebasing
   instead of taking the frame down.
2. The plan tests no entity kind at all. Added: circle keeps its radius while
   its centre is rebased, arc keeps radius and both angles, point draws as a
   point, polyline draws every vertex. Rebasing a radius or an angle is the
   error the payload's own doc comment warns about.
3. Added culling (the query must use `camera.visibleWorld`, not the document
   extents), the resolved style reaching the sink, and a large-coordinate
   locality assertion — the plan's fixture sits at 1000/2000, where rebasing
   proves nothing.
4. `closed` is always false: the model has no closed-polyline flag. A DXF
   LWPOLYLINE has one, so this is a model gap for the DXF plan, recorded in
   the code and pinned by a test, not a decision made in the painter.

**Engine defect found and fixed here (jet_cad_2d, outside Task 6's file
list):** `EntityFlags.invisible` — DXF group code 60 — had a column, a
constant and a test asserting its bit value, and no query read it.
`FilterEvaluator.acceptsEntity` checked the layer and the owner chain only, so
an entity marked not-drawn was drawn by the renderer and selectable by a
click. Fixed in the evaluator rather than in the painter: doing it in the
painter would leave picking wrong and duplicate the filter. Engine test added;
619 tests pass.

Mutation check on Task 6: rebasing by the world origin, ignoring

Task 7: complete. Leaves and instances merge into one ascending-handle stream.
54 tests in the Flutter package, analyze and format clean.

Task 7 notes and deviations:
1. `BeginResidualOp.debugHandle` is a `Handle` defaulting to `Handle.none`, not
   a `Handle?`. `Handle` is an extension type over `int` and the codebase
   already rules against nullable handles (see `Handle.none`'s doc comment:
   a nullable handle and an implicit zero would both appear and diverge).
   `DrawSink.beginResidual` grew an optional named parameter to carry it;
   `==` and `hashCode` ignore it, pinned by a test.
2. The plan tests one interleaving, [leaf, instance, leaf], which never reaches
   the flush-before-the-first-leaf path, the tail drain after the leaf stream
   ends, or the difference between `while` and `if` in the flush. One test per
   branch added, plus buffer growth past the initial 64 with the entries that
   arrive after the growth still drawn.
3. `_worldRect`, which the plan introduces here, is left out until Task 8
   actually reads it — a field and a getter no test can reach is dead code.
4. `_drawInstance` pushes the instance's residual and its place in the draw
   order, and draws no contents: Task 8 adds the descent. Until then an
   instance is a correctly-ordered empty residual, which is why Task 8 must
   land before any rig runs.
Mutation check: dropping the merge, `while`→`if` in the flush, dropping the
tail drain, and growing the buffer without carrying the old entries over each
fail the suite.

Task 8: complete. The painter descends into definitions. 65 tests in the
Flutter package, 619 in the engine, analyze and format clean.

Task 8 decisions and deviations:
1. An instance pushes **no residual of its own**. Every leaf it reaches pushes
   the whole chain, so wrapping them in the instance's transform too would
   apply it twice. Task 7's stub did push one, and Task 7's order tests are
   rewritten here: the handle that shows up at an instance's position in the
   draw order is now its definition's content handle.
2. The plan's `_placedInstances` has no definition, and the only public route
   from an instance handle to its transform is `transformOfInstance`, a linear
   `indexOf` — quadratic per container, which the plan itself rules out.
   `_DepthScratch.collectInstances` instead collects visible handles from
   `searchInstances`, sorts them, and makes **one** pass over the container's
   instance array, binary-searching each handle into the sorted set to fill in
   its position. O(n log k) per container visit, no engine change, no map.
3. `searchLeaves` duplicates are dropped by comparing each handle with the
   previous one after the sort — no set, no allocation. The test constructs
   the documented condition directly, putting a live slot into the container's
   dirty overlay.
4. A `maxDepth` of 64 with a counter, `skippedDeepInstanceCount`. The tree
   rejects cycles so it should be unreachable, but this recursion runs on the
   frame path, where unbounded depth is a stack overflow rather than a wrong
   picture — and a silent cut-off would read as a complete frame. Same
   principle as the text counter in Task 6.
5. Added beyond the plan: an instance nested inside a definition is descended
   into; the query rectangle is expressed in the container's own space (a
   fixture at the origin cannot tell); a singular instance transform does not
   throw; BYBLOCK contents take the instance colour, and a nested BYBLOCK
   instance takes the outer one's — Task 2's resolver reaching the painter;
   and two consecutive frames produce identical op lists, which is the first
   thing the Task 11 oracle will rely on.
Mutation check: dropping the dedupe, the sort, the local-space rectangle, the
`accumulated . instance` composition order, the inherited style context, and
the depth cap each fail exactly one test.

Task 9: complete. Lineweight stays a paper quantity; leaves past
`kAnisotropyThreshold` take the exact per-axis path. 75 tests in the Flutter
package, analyze and format clean.

Task 9 findings and deviations:
1. **The bypass cannot carry curves.** An anisotropic transform turns a circle
   into an ellipse and `DrawSink.circle` carries one radius, so circles and
   arcs stay on the residual path — where `Canvas` draws the ellipse correctly
   and only the stroke width is approximate, by up to the anisotropy ratio.
   Counted as `anisotropicCurveCount` rather than left implicit. The plan does
   not mention this; it specifies the bypass for "the points", which curves do
   not have.
2. Anisotropy is measured on `camera . placement`, the transform whose units
   `Paint.strokeWidth` actually lives in, not on the placement alone. With a
   conformal camera the two agree, so no test can currently tell them apart —
   recorded here rather than left to look arbitrary.
3. The plan's tests check the bypass's stroke width and residual shape but
   never that it draws in the right *place*, and never that it hands the sink
   small numbers. Both added. The second matters: rebasing the bypass in world
   space instead of screen space reconstructs to the identical position — the
   residual carries whatever was subtracted — so only a magnitude assertion
   catches it. It survived the first mutation round for exactly that reason.
4. `Paint.strokeWidth` is a float32 on the `dart:ui` side. Width assertions are
   to 1e-6, not 1e-9; the first draft failed at 7.6e-8.
Mutation check: removing the bypass, rebasing it in world space, and letting
curves take it each fail the suite.

Plan deviation ruled by human (2026-08-10): `contextFor` now substitutes layer 0
BEFORE reading the instance's own BYLAYER colour, where the reference passed
`node.layer` raw. Under the reference a single instance reported two effective
layers — layer 0 for its own colour, the substituted layer for everything it
placed. Pinned by "a nested instance on layer 0 resolves ByLayer against the
substituted layer".

Task 10: complete. `LeafOwnerMap` plus the cull-floor shortcut in the painter.
92 tests in the Flutter package, 619 in the engine, analyze and format clean.
Done on `main` directly — tasks 0-9 were merged at f9a7d8e first.

Task 10 findings and deviations:
1. **The plan's Step 4 shortcut is unsafe as written.** `slotsOf(container)`
   answers for the leaves a container owns *directly*, while its
   `ContainerIndex` also holds every leaf folded up out of the groups nested
   inside it — those are owned by the group node. Taking the bucket for a
   definition with a nested group would silently drop those leaves. The
   shortcut now also requires `bucket.length == ci.leafCount`, which rules
   that out and, for free, rules out a container edited since the index was
   built (its new leaves live in the dirty overlay, not in `leafCount`).
2. `ownerMap` is optional on `DraftPainter` and the shortcut is taken only
   when supplied. A map is only as good as the changes fed to it; opt-in means
   a caller that forgets gets the slower path rather than a stale picture.
3. The plan's `_forgetRemoved` scans every bucket for slots that are no longer
   live. A drag is spelled as remove-then-add per pointer sample, so that scan
   would run at pointer rate. Replaced by a `handle -> slot` map, so removal is
   a lookup, plus an `slot -> owner` map so dropping is a binary search rather
   than a walk over every owner.
4. Slot reuse: the free list hands a removed entity's slot to the next added
   one, so `_reconcile` drops whatever is already filed under that slot before
   inserting. The plan does not do this and has no test for it; without it the
   new entity draws inside the old owner.
5. The plan tests no removal at all. Added: removal, slot reuse across owners,
   undo, `DocumentLoaded`, an empty `touched` set, and a run of twelve adds,
   four removals and an undo compared against a full derivation.
Mutation check: forgetting nothing on removal, dropping the reused-slot
defence, unsorted buckets, and removing either cull-floor guard each fail the
suite.

Ruling (human, 2026-08-10) on Task 5's open question: **option A**.
`BeginResidualOp.==` stays exact; tolerance belongs in the oracle's matcher,
not in the value type. A tolerant `==` breaks the `hashCode` contract and is
not transitive, and exactness is what makes the mutation checks bite.

Measured, so Task 11 and Plan 3b can be written against real numbers. One
definition placed 500 times at 4.5e6, comparing today's flat chain against the
regrouping Plan 3b's picture cache will do — `(camera . instance) .
(leaf . rebase)` instead of `camera . instance . leaf . rebase`:

  chain translation magnitude              ~263 px (screen space, as intended)
  worst screen delta of a drawn point      9.8e-9 px
  chains unequal under Tolerance.standard  417 / 500
  chains unequal under exact ==            500 / 500

So floating-point regrouping moves a drawn point by about one hundred-millionth
of a pixel, and **`Tolerance.standard`'s `linear: 1e-9` is too tight** to call
that equal at this magnitude. Task 11's step 4 names
`Tolerance.defaultTolerance`, which does not exist — the constant is
`Tolerance.standard`. The oracle's matcher should use an explicit screen
tolerance of 1e-6 px: a hundred times the observed drift, a thousandth of a
visible pixel.

Task 11: complete. `referenceWalk` in lib, the fixture and the comparison in
test/support. 101 tests in the Flutter package, 619 in the engine, analyze and
format clean.

Task 11 decisions and deviations:
1. **The comparison is in screen space, not op space.** The plan's signature
   takes the world view rect and matches "op kind, style and geometry"; that
   cannot work as written, because the painter's anisotropy bypass hands the
   sink screen-space points under a translation-only residual where the
   reference hands it local points under a full one. Both draw the same line.
   `flatten` applies each residual to the geometry drawn under it, and the
   match runs on the result, with the viewport rect for the off-screen check.
2. Tolerance is `kScreenTolerance = 1e-6` px, from the measurement recorded
   above — not `Tolerance.standard`, whose 1e-9 fails 417 of 500 chains on
   arithmetic noise alone. A test pins that 1e-9-scale jitter passes and a
   half-pixel shift fails.
3. The reference deliberately does **not** bypass, does not use the cull floor,
   and builds no index. It agrees with the painter on the document, the camera
   and the rebase origin only, because those three are inputs rather than
   answers.
4. Added beyond the plan: a non-vacuity test (a superset assertion passes
   trivially against an empty reference), and four tests that feed the
   comparison a deliberately damaged op list — a dropped op, a reordered pair,
   a half-pixel residual shift, and sub-tolerance jitter — so the comparison
   itself is known to bite.
Mutation check on the painter: inward-out composition in `_descend`, ignoring
the folded group transform, and dropping the instance merge each fail the
differential test.

## Task 12b — mutation testing on the arithmetic and the ordering

Log: `docs/superpowers/notes/plan-3a-mutation-log.md`. Fourteen mutants, each
applied to the source by hand and reverted: the plan's ten plus 1b (the plan's
own rebase composition, kept as a mutant because the implementation deviates
from it), 6b, 4b and 8b.

Thirteen were killed by existing tests. One survived.

**Mutant 3 (`<` -> `<=` in the root merge) survived, and the cause was not a
missing test.** The two comparisons differ only when a root-level instance
handle equals a leaf entity handle, and no fixture could produce that tie
because -- as it turned out -- nothing prevented it either. `AddEntityCommand`
checked only `entities.containsHandle`; `AddNodeCommand` checked only
`tree[handle]`. Neither checked the other store, so one handle naming both an
entity and a node was accepted, against DXF's global uniqueness and against
this codebase's own shared `handleSeed`.

Deviation from the plan's Step 2 ("fix the fixture, not the assertion"): the
fixture is not what is wrong here. Fixed the invariant instead --

- both commands now cross-check the other store, entity-side before
  `geometry.add` so a rejection leaks no slot;
- three tests in `commands_test.dart` (`handles are one space, not two`),
  including one pinning that undo returns a handle to the other store;
- `DraftPainter.paint` documents the invariant its comparison depends on.

Two existing engine fixtures were genuinely colliding and the guard caught
them: `container_index_test.dart` interleaved a written-out `Handle(1000 + i)`
loop with seeded `addLine` calls, and `pick_test.dart` wrote out `Handle(402)`
after `addEntity` had been handed 402. Both now allocate from the seed; neither
asserted on the values. Both had been building malformed documents silently.

With the guard, mutant 3 is equivalent -- no reachable document distinguishes
the two comparisons. Removing either half of the guard is killed by its own
test, checked.

Suite: engine 619 -> 622, Flutter 106 unchanged. Both green, analyze clean.

Deviations:

Colour is written out as `TrueColor(0x000000)`, not ByLayer: layer 0 resolves

## Task 13 — DraftCanvas and the damage model

`lib/src/draft_canvas.dart` (`DocChangeNotifier`, `DraftCanvas`,
`DraftCanvasState`), 11 tests in `test/draft_canvas_test.dart`.

Deviations and additions:
1. **`DraftCanvasState` is public.** The plan's tests reach `paintCountOf`,
   which needs a hook into the widget. Rather than a test-only field on a
   production class, the State is public with `painter`, `ownerMap` and `sink`
   getters -- the `ScaffoldState`/`FormState` idiom. Paint scheduling itself is
   asserted through `RenderCustomPaint.debugNeedsPaint`, which is supported
   debug API and needs no hook at all.
2. **The camera test asserts a repaint *was* scheduled**, not only that no
   rebuild happened. The plan's version passes on a canvas that neither
   rebuilds nor repaints -- a frozen canvas.
3. **`DocChangeNotifier` forwards before it notifies**, with a test pinning the
   order. A listener repaints and a repaint reads the map; notifying first
   would draw one frame against a map that does not know about the edit.
4. **Added `pixelsPerPaperMm`** (default `kLogicalPixelsPerMm = 96/25.4`) and
   an optional `resolver`. The plan's constructor omits both, and a lineweight
   cannot become pixels without a paper-to-screen scale.
5. **One `CanvasDrawSink` for the widget's life, its `Canvas` rebound per
   paint.** The plan has the State hold one `DraftPainter` and one
   `LeafOwnerMap`; the same reasoning covers the sink and the plan missed it.
   A sink built per paint allocates a `Paint`, a `Path` and two typed lists
   every frame -- the four allocations the sink exists to avoid.
   `CanvasDrawSink`'s constructor takes `canvas` as an optional named argument
   and the field is `late` and mutable; three call sites updated.
6. **Nothing handed in is disposed** (document, index, camera), with a test:
   two canvases over one document is the split-view case.

Mutation round, eight mutants, all killed:

| Mutant | Killed by |
|---|---|
| canvas claims `onAfterMutate` | `does not claim commands.onAfterMutate` |
| `shouldRepaint` returns true | `the painter never repaints per vsync` |
| notify before forwarding | `DocChangeNotifier forwards before it notifies` |
| `repaint: null` | camera and document repaint tests |
| owner map not fed | `each change reaches the leaf-owner map` |
| `dispose` leaks the subscription | `disposing stops listening` (after rewrite) |
| notifier disposed, stream not cancelled | that test plus the notifier's own |
| a sink built per paint | `one sink serves every paint` (after rewrite) |

Two of those survived their first test and both survivals were the same
mistake -- asserting a proxy instead of the property:

- `disposing stops listening` first asserted only `takeException() is null`. A
  leaked subscription does not throw; it quietly keeps a dead canvas
  maintaining derived state. Rewritten to hold the `LeafOwnerMap` across the
  disposal and assert it stops changing.
- `one sink serves every paint` first asserted only that `state.sink` was the

## Task 14 — corpus extensions, all off by default

Seven parameters on `generateDocument`, 12 tests.

Deviations:
1. **The "no default leaked" guard is a fingerprint, not the plan's structural
   assertions.** The plan checks one layer, every colour ByLayer, every node an
   instance under the root -- all of which pass on a document whose coordinates
   have all moved. Instead `DraftDocumentCodec.encodeToString` is hashed
   (FNV-1a) and pinned. The two literals were taken from the generator
   *before* any extension was written, which is the only ordering that makes
   them evidence. Both structural and fingerprint checks are kept; the
   structural one says *which* property moved when the fingerprint breaks.
2. **A second `math.Random`.** Every extension draws from `extra` and allocates
   no handle while it is zero, so the primary stream is untouched no matter how
   many extensions are added later. One stray draw on the primary stream would
   shift every value after it.
3. **Fractions are quotas, not coin flips.** Written as `nextDouble() < f`,
   `mirroredFraction: 0.25` over 500 instances came out **0.308** -- three
   standard deviations off, and a rig cannot tell that from a real difference.
   The fraction specifies the corpus, so an accumulator is used instead and the
   count lands exactly. Same for `dashedFraction` and `byBlockFraction`.
4. **`nonUniformFraction` scales past `kAnisotropyThreshold` (2.0) on
   purpose.** A gently squashed instance measures the fast path and would be
   reported as coverage of the exact one.
5. **`byBlockFraction` applies to definition-owned entities only**, with a test.
   Root-level ByBlock has no instance to resolve against, so it resolves to the
   context and exercises no extra path -- it would inflate the fraction while
   measuring nothing.
6. **Groups hold local geometry**, with the floor position in the group's own
   transform. Authoring group contents at floor coordinates would move the
   whole cluster by the plan's width once the transform composed.
7. **Added `nesting terminates: no definition reaches itself`.** The plan tests
   that nesting happened, not that it is acyclic. A cycle here is a stack
   overflow on the frame path, not a slow document. The generator chains
   definitions in index order, which is what makes a cycle unconstructible; the
   test says so rather than the comment.
8. Extra layers get concrete distinct colours and lineweights. Records nothing
   resolves against measure the table, not the resolution path.

Benchmark re-run (the plan's real check). Four runs, medians against the gate
note's recorded post-fix values:

| Row | recorded p50 / p95 | today p50 / p95 |
|---|---|---|
| forEachInRect fresh | 0.672 / 0.778 | 0.692 / 0.777 |
| pick fresh | 0.348 / 0.408 | 0.330 / 0.369 |
| snap fresh | 0.550 / 0.664 | 0.530 / 0.686 |
| forEachInRect dirty | 0.856 / 1.029 | 0.841 / 0.931 |
| pick dirty | 0.493 / 0.617 | 0.541 / 0.660 |
| snap dirty | 0.883 / 1.100 | 0.889 / 1.092 |

Every row inside ±10%. The first run alone showed `snap fresh` p95 at 1.010 ms

## Task 15 — rigs R1 and R3

`test/rig/paint_microbench_test.dart`, `dart_test.yaml` (rig tag), `README.md`,

2. **`tags: {rig: {skip: ...}}` skips unconditionally.** `--tags rig` selects

4. **The owner-map variant is measured.** The plan's rig passes no
   `ownerMap`, so `directBucketCount` reads 0 — which looks like a dead feature

5. **`measure` is capped by wall clock** (20 s, minimum 12 samples, sample

6. `MemoisedStyleResolver` keys on a **record of every context field**, not on

## Task 16 — harness app, R2, R4a and R4b

`apps/dev_harness_2d` (macOS), added to the workspace. 35 files, most of them
the Xcode scaffolding `flutter create` writes, matching `apps/dev_harness`.

Deviations:
1. **`flutter test --profile` does not exist.** The plan's command is rejected
   by Flutter 3.44: `Could not find an option named "--profile"`. Profile-mode
   frame timings only come out of a real run on a device, so the rigs run
   through `flutter drive` with a `test_driver/integration_test.dart`. Both
   commands are in the app's README and the package README.
2. **The rigs measure the command's own wall clock, not just frame timings.**
   This is the deviation that changed the conclusion. A command runs
   synchronously in the gesture handler, *before* the frame it causes, so the
   index invalidation it triggers never appears in `buildDuration`. The plan's
   R4b reports "200 rebuilds" and a 5.4 ms build time side by side, which reads
   as "a full rebuild is free". It is not: the rebuild costs **115.8 ms per
   gesture step** at 50k, and none of it is visible in a frame timing.
3. **The rigs boot to the working set, not to the whole drawing.** R1 already
   reports the fit-everything frame at about a second; repeating it here would
   have measured the same thing twice and neither time a frame anyone renders.
4. `HarnessApp` takes an `onReady` callback so a rig can drive the camera and
   read the index. The alternative — globals in `main.dart` — is what the
   plan's sketch implies and it makes the app's own behaviour depend on which
   rig last ran.

### Results (M3 Pro, macOS, profile mode, working-set camera)

|---|---|---|---|

|---|---|---|---|

### What these say

**The render path is raster-bound, not walk-bound.** Raster is 14x build at 50k
(78 vs 5.5 ms) and 17x at 500k (183 vs 10.7 ms). R1's microbench cannot see
this at all — `PictureRecorder` records without rasterising — so the two rig
families disagree by construction and the profile-mode one is the true one.
Roughly 11,000 ops per frame at 50k and 21,000 at 500k, each leaf carrying its
own `save`/`transform`/`restore`. Plan 3b's target is the draw calls, not the
walk.

**Dragging a leaf is free. Dragging an instance is a second of blocked UI.**
0.10 ms against 957.98 ms at 500k, and 0.12 against 115.84 at 50k — a factor of
about a thousand either way. A leaf edit lands in the dirty overlay: one entry,
zero rebuilds, threshold nowhere near. `TransformNodeCommand` touches a node
handle, which the index classifies as structural and answers with a full
rebuild — one per gesture sample. Moving a block is the application's defining
gesture and it currently costs a second per pointer move at 500k.

**Neither number appears in a frame timing.** Commands run synchronously in the
gesture handler, before the frame they cause. The plan's R4b prints "200
rebuilds" and "build p50 5.4 ms" side by side; read as written, Plan 3a would
have closed with "frames are fine".

**The macOS harness stalls when backgrounded.** Two background `flutter drive`
runs hung on the first `pumpWidget` at 0% CPU with no timeout — 46 minutes on
the first. Two foreground runs of the same command completed. `RIG` and `STEPS`
were added so one rig fits in one foreground run; both READMEs say so.

Also recorded: R4a burns 201 handles over 200 steps, because a drag is
remove-then-add — there is no in-place geometry command. Every pointer sample
of a real drag leaks a handle and a slot.
